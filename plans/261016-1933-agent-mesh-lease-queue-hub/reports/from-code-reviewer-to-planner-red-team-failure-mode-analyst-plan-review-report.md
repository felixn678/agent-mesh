# Red Team: Failure Mode Analyst — AgentMesh plan review

Scope: plan.md, phase-01..05, handoff, researcher reports (go-hub-stack, dispatch). Plan-only review; no code exists.

## Finding 1: Non-idempotent complete + spool replay closes the GOOD PR
- **Severity:** Critical
- **Location:** phase-01 Key SQL (complete); phase-03 Per-task flow, publish steps 6 and spool
- **Flaw:** Complete only matches `state='running'`; any second delivery of a complete that the hub already committed returns 409. The daemon treats every complete-409 as "lease lost" and closes the PR.
- **Failure scenario:** Mac sends complete(fence 1). The hub commits `state='done'`, but the response is lost (wifi blip, hub restarts right after commit, client timeout). The daemon sees a network error, spools the record and replays it. Replay gets 0 rows because state is now `done`, so 409. Per step 6 the daemon runs `gh pr close <url> --comment "lease lost; superseded"`. The only valid PR gets closed while the hub shows `done` with that pr_url. The same thing happens with a client-side timeout on a slow `SetMaxOpenConns(1)` hub. Lost claim responses have the same problem: the task sits `running` with no runner, then gets reclaimed with `attempts+1`. Network flaps alone can push a task to `stuck` without any real run.
- **Evidence:** phase-01-hub-core-and-lease-queue.md:128 `Complete / fail: same WHERE id AND fence AND claimed_by AND state='running' ... 0 rows → ErrLeaseLost → HTTP 409.`; phase-03-host-daemon-and-claude-runner.md:89-90 `6 complete(...) 409 → gh pr close <url> --comment "lease lost; superseded" ; STOP`; :92 `any hub network error in 3/6 → spool record ..., retry with backoff; replay on daemon start`
- **Suggested fix:** Make complete/fail idempotent. If `state IN ('done','stuck','queued') AND fence=:fence AND claimed_by=:host` and the stored outcome matches, return 200 (or a distinct `already_applied`). Return 409 only when `fence != :fence` or `claimed_by != :host`. Add a distinct 409 body code (`lease_lost` vs `cancelled`) and close the PR only on `lease_lost`. Add a test: commit the complete, drop the response, replay, and assert the PR stays open.

## Finding 2: Side effects happen before the intent is persisted; a crash between push/PR and spool causes duplicate PRs
- **Severity:** Critical
- **Location:** phase-03 publish steps 4-6 + spool; plan.md acceptance "zero duplicate PRs"
- **Flaw:** The spool is written only after a hub network error, and the record schema has no branch or pr_url. A daemon crash (OOM, launchd/systemd restart, reboot, Mac sleep followed by a kill) after `gh pr create` and before complete leaves an open PR that no surviving state knows about. Even a spooled step-6 record cannot close the PR on 409 because the URL is not stored.
- **Failure scenario:** Daemon pushes `agentmesh/task-7-f1` and opens draft PR #40, then gets SIGKILLed (install.sh upgrade, `systemctl --user restart`, power). There is no spool record. The lease expires after 5 min. Ubuntu reclaims at f2, runs again and opens PR #41. Two open PRs for task 7, which violates the soak criterion. Separately, on complete-409 the `gh pr close` call is itself a network call with no retry or spool. If it fails, the zombie PR stays open forever.
- **Evidence:** phase-03-host-daemon-and-claude-runner.md:92 `spool record {task,fence,wt,result,step}` (no pr_url/branch); :86-89 push → `gh pr create` → complete; plan.md:78 `Overnight soak (both hosts): zero duplicate PRs`
- **Suggested fix:** Use a write-ahead journal: fsync a spool record with `{step, branch, pr_url}` before each external side effect and update it after. Replay must cover "pushed but no PR" and "PR but not completed". Also make each new attempt supersede older ones: before `gh pr create`, run `gh pr list --head 'agentmesh/task-<id>-f*' --state open` and close PRs from older fences, or reuse the open one. Retry `pr close` from the spool until it succeeds.

## Finding 3: Worktree leak drives the host into a permanent self-DoS through `max_worktrees`
- **Severity:** High
- **Location:** phase-03 Per-task flow (409 / timeout / crash / is_error paths); Load + thresholds; config `max_worktrees = 6`
- **Flaw:** Only the happy path (step 7) removes a worktree. The 409, timeout, crash-retry, is_error, allowlist and gh-error paths all keep it. Each retry gets a new fence-named worktree. Worktrees count against `max_worktrees`, which also counts the human's worktrees. Nothing does GC, and the 409 path sends no report, so the hub never learns where the zombie worktree is. Logs (`stream-json --verbose`, per attempt) are never rotated either.
- **Failure scenario:** On the Mac, two sleep-induced 409s plus one timeout plus the human's 3 worktrees add up to 6. `worktrees < max` is now false forever, so the Mac silently stops claiming. The hosts table still shows the Mac as alive and healthy-looking, and the report never says why it went idle. On Ubuntu, a crash-loop task with `max_attempts=3` leaves 3 full checkouts per task, and with `node_modules`-sized repos the disk fills overnight.
- **Evidence:** phase-03-host-daemon-and-claude-runner.md:75 `409 → SIGTERM pgroup, SIGKILL +30s, keep worktree, STOP (no push, no report)`; :85 `409 → STOP, keep worktree, no push`; :91 `7 git worktree remove <wt>` (happy path only); :32 `max_worktrees = 6 # all worktrees across configured repos, incl. human ones`; :102 `Claim iff ... worktrees < max`
- **Suggested fix:** Add a retention policy. Delete worktrees for 409/superseded attempts immediately: the commits are worthless because another fence owns the task. Keep stuck worktrees for N days, then `git worktree remove --force` + `git worktree prune` at daemon start and daily. Count only `agentmesh/*` worktrees toward the daemon's own cap, and keep a separate human budget. Report `claim_blocked_reason` in the hosts load so the report shows why a host is idle. Rotate or cap logs.

## Finding 4: Git lock contention: push, commit and gc run outside the per-repo mutex on the human's live clone
- **Severity:** High
- **Location:** phase-03 Per-task flow line 73 (mutex scope); publish step 4; Risk table "Concurrent git ops"
- **Flaw:** The mutex covers only fetch / worktree add / worktree remove. `git push -u` writes the shared `.git/config` (`config.lock`). Concurrent claude `git commit` runs in sibling worktrees, and the human's own git use in the same clone (the `[repos]` path is the human's working repo), can trigger `git gc --auto` / `pack-refs`, which takes `gc.pid` and `packed-refs.lock`. `git branch -D` (step 7) also edits config and refs. The mutex is also in-process only, so it does not protect against the human or claude. Push failure handling is undefined. Fetch and push credentials under systemd/launchd (no ssh-agent socket) are not preflighted; only `gh auth status` is.
- **Failure scenario:** Ubuntu runs `max_concurrent=3`. Two tasks finish within seconds of each other, and both `git push -u` calls race on `.git/config`. One fails with `could not lock config file .git/config: File exists`. The plan has no branch for push failure: the daemon either completes with no branch (work lost from the report) or crashes the goroutine and leaks the lease. Overnight, the auto-gc triggered by many claude commits makes the human's morning `git commit` fail with `Unable to create '.../packed-refs.lock'`.
- **Evidence:** phase-03-host-daemon-and-claude-runner.md:73 `lock repo; git fetch origin <base>; git worktree add ...; unlock`; :86 `4 git push -u origin <branch>` (outside lock, no error branch); :153 `Concurrent git ops on same repo lock errors | M×M | per-repo mutex for fetch/worktree add/remove`; :40 `agent-mesh = "~/Code/agent-mesh"` (human clone); :131 preflight only `gh auth status`
- **Suggested fix:** Use a dedicated daemon-owned clone per repo (`<state_dir>/repos/<repo>.git`, with `gc.auto=0` and a scheduled `git gc` under the mutex) instead of the human's clone. Push without `-u` (`git push origin HEAD:refs/heads/<branch>`) so config is never written. Put push and branch -D under the mutex. Define push failure as a retry with backoff, then `fail(retry=true, "push: ...")`. Preflight `git ls-remote origin` under the service environment.

## Finding 5: Orphaned claude on Mac after a daemon crash (Setpgid escapes launchd cleanup) runs alongside the reclaimed copy
- **Severity:** High
- **Location:** phase-03 Runner command (`Setpgid:true`); Risk "Daemon restart kills running claude"; phase-05 LaunchAgent `KeepAlive`
- **Flaw:** The risk table assumes a daemon restart kills claude, which is true only for the systemd cgroup. launchd kills only the job's process group on exit (AbandonProcessGroup semantics). `Setpgid:true` deliberately puts claude in its own group, so on the Mac claude survives a daemon crash. The restarted daemon has no adoption logic: no pid file, no scan of `state_dir/logs`, no reconciliation of running leases. The tmux mode makes this worse: the tmux server outlives the daemon on both OSes once it is reparented.
- **Failure scenario:** The Mac daemon panics at 02:00 and KeepAlive restarts it. The orphan claude for task 9/f1 keeps editing its worktree and spending up to `max_budget_usd`. With no heartbeat, the lease expires and Ubuntu reclaims at f2. Two claudes now run the same task, and the orphan's spend never reaches `cost_usd`. If the orphan ignores the "do not push" prompt (`allowed_tools` empty means default tools, and nothing blocks Bash git push), it pushes `task-9-f1` with no gate at all. On the Mac, which already lags, the orphan also consumes the single `max_concurrent=1` slot while the daemon thinks `running=0` and claims another task.
- **Evidence:** phase-03-host-daemon-and-claude-runner.md:113 `SysProcAttr{Setpgid:true}; kill(-pgid)`; :154 `Daemon restart kills running claude (systemd cgroup) | M×L | accepted`; phase-05-install-and-ops.md:23 `KeepAlive`, `RunAtLoad`
- **Suggested fix:** Write a per-task run record (`pid`, `pgid`, `id`, `fence`, `wt`) before starting claude. On daemon start, for each record either kill the pgid or re-adopt it (resume heartbeating with the stored fence, and kill it on 409). Count live orphans in `running` and in the slot accounting. Define SIGTERM handling for the daemon: kill children and send fail(retry=true, "daemon shutdown") within `TimeoutStopSec`. Pass `--disallowedTools "Bash(git push*)"` explicitly instead of relying on the prompt.

## Finding 6: Hub boot path: binding to the LAN IP fails at boot, and every crash-restart re-runs grace and extends dead leases
- **Severity:** High
- **Location:** phase-01 Grace SQL + startup order; phase-05 systemd user unit `Restart=on-failure`, `listen = "<hub-lan-ip>:8787"`
- **Flaw:** (a) The startup order is open → migrate → grace → reaper → listen. A systemd user unit with linger starts before the LAN address exists, because user units cannot order on the system `network-online.target`. The bind fails with EADDRNOTAVAIL, the process exits, and `Restart=on-failure` loops until StartLimitBurst (5/10 s) gives up. The hub then stays dead until someone intervenes, which breaks the "Ubuntu reboot → hub running" criterion. (b) Each failed start has already run grace first. `MAX(lease_expires_at, now+ttl)` is applied to every `running` row, including leases held by daemons that are long dead, so any crash loop or flapping hub postpones reclaim indefinitely. (c) Grace uses the hub wall clock at boot. If the RTC is wrong and NTP later steps the clock forward, every lease instantly looks expired, the reaper stucks at-cap tasks, and live work gets reclaimed. That is a duplicate run, even though the plan claims clock skew is L×L.
- **Evidence:** phase-01-hub-core-and-lease-queue.md:129 `Grace (hub start): UPDATE tasks SET lease_expires_at=MAX(lease_expires_at, :now+:ttl) WHERE state='running'`; :172 `startup: open → migrate → grace → reaper ticker → listen`; :198 `Clock skew | L×L | hub-only clock`; phase-05-install-and-ops.md:21 `Restart=on-failure`; :24 `listen = "<hub-lan-ip>:8787"`
- **Suggested fix:** Listen first, then grace. Grace only leases whose `lease_expires_at` falls within the hub downtime window, using a persisted `last_alive_at` heartbeat row written every reaper tick, and extend by `min(downtime, ttl)`, not unconditionally. Bind with `IP_FREEBIND` or listen on `0.0.0.0` with ufw. Alternatively, retry the bind in-process for 2 min before exiting, and set `RestartSec=5`, `StartLimitIntervalSec=0`. Use the monotonic clock for lease deltas within a process. If skew stays out of scope, at least run the reaper on `now` only after `timedatectl` reports synced.

## Finding 7: Fence and ID monotonicity are not durable (`synchronous=NORMAL`, rowid reuse, restore from daily backup)
- **Severity:** High
- **Location:** phase-01 DSN + schema `id INTEGER PRIMARY KEY`; Rollback row; phase-05 Backup / DB corruption mitigation
- **Flaw:** The whole zombie defense is "unique branch `task-<id>-f<fence>`". It assumes `(id, fence)` is never reissued. Three things break that. WAL with `synchronous=NORMAL` can lose the last committed transactions on power loss, after the hub has already returned the fence to a daemon. `INTEGER PRIMARY KEY` without `AUTOINCREMENT` reuses ids after any delete or restore. And the documented recovery path, restoring the daily `.backup`, rolls fences and ids back by up to 24 h.
- **Failure scenario:** Ubuntu loses power just after the hub commits claim 15/f2 for the Mac and returns it. On reboot the commit is gone: task 15 is back to queued at fence 1, and Ubuntu claims 15/f2 again. The Mac and Ubuntu now both hold "f2". `claimed_by` blocks the Mac's complete, but the Mac has already pushed `agentmesh/task-15-f2` after a heartbeat that raced before the loss, and Ubuntu's push to the same branch name then fails non-fast-forward. In the restore case, new task ids 30-45 collide with existing remote branches and PRs `agentmesh/task-30-f1`, so pushes are rejected or PRs get cross-linked to the wrong tasks.
- **Evidence:** phase-01-hub-core-and-lease-queue.md:107 `_pragma=synchronous(NORMAL)`; :76 `id INTEGER PRIMARY KEY,`; :199 `DB: delete file (no prod data yet)`; phase-03-host-daemon-and-claude-runner.md:97 `Unique branch task-<id>-f<fence> means even a zombie push can never overwrite another attempt's branch`; phase-05-install-and-ops.md:25,67 daily `.backup` ×7 as DB corruption mitigation
- **Suggested fix:** Use `synchronous=FULL`; the write rate is tiny. Use `AUTOINCREMENT`. Add a per-hub `epoch` (random, regenerated on restore or new DB) to the branch name, or derive fence from a global monotonic counter persisted with FULL sync. Document a restore runbook: bump epoch, then mark restored `running` rows as `stuck` with reason "restored". Push with `--force-with-lease=<branch>:` (expect absent) so collisions fail loudly and map to `fail(retry=false)`.

## Finding 8: Host-side allowlist rejection permanently kills tasks another host could run
- **Severity:** Medium
- **Location:** phase-03 Requirements "Host-side authority"; Per-task flow line 72
- **Flaw:** The claim filters only on repo and host. Permission mode and budget cap are checked after claiming, and rejection is `fail(retry=false)`, which leads to `stuck`. Each host has its own `allowed_permission_modes` and `max_budget_usd_cap`, so whichever host polls first decides the task's fate.
- **Failure scenario:** A task is added with budget $8 and no host constraint. Ubuntu's cap is 10 and the Mac's is 5 (the example config). The Mac polls first, claims it, rejects it, and the task goes `stuck`. Ubuntu never sees it. Every 30 s poll race is a coin flip, and the morning report shows a stuck task that was perfectly runnable. The rejection also burns an attempt and a fence.
- **Evidence:** phase-03-host-daemon-and-claude-runner.md:42 `reject claimed task (fail retry=false, reason) if permission_mode not allowed or budget > cap`; :72 `claim → validate vs host allowlist ──reject──> fail(retry=false)`; phase-01-hub-core-and-lease-queue.md:115-120 claim WHERE has only repo/host/attempts predicates
- **Suggested fix:** Send `permission_modes[]` and `max_budget` in the claim request and add `AND permission_mode IN (json_each(:modes)) AND max_budget_usd <= :cap` to the subquery. Keep the post-claim check as defense in depth, but release with a non-attempt-consuming `release` (decrement attempts, back to queued) instead of fail→stuck.

## Finding 9: Expired below-cap leases with no eligible claimer stay `running` forever; the reaper never sees them
- **Severity:** Medium
- **Location:** phase-01 Reap SQL; claim WHERE; phase-04 Running section
- **Flaw:** Recovery from an expired lease depends entirely on some daemon claiming the task. The reaper only acts at `attempts>=max_attempts`. Tasks with `host='mac'`, or a repo only one host maps, sit `running` with an expired lease indefinitely while that host is asleep, dead or excluded (the phase-3 NO-GO makes v1 Ubuntu-only). Combined with the heartbeat dropping the expiry predicate, a host that wakes days later resumes an "exclusive" lease with stale claude context and pushes a PR against a base that moved long ago.
- **Failure scenario:** A task is enqueued with `host="mac"` (phase-5 step 6), and the Mac's lid stays closed all weekend. The report shows `#12 running mac lease expires in -54h`, with no stuck reason and no alert. Monday the Mac wakes, its heartbeat succeeds (fence authority), and the claude session resumes. Its context has a 3-day gap, and the result gets published as if fresh.
- **Evidence:** phase-01-hub-core-and-lease-queue.md:130 `Reap: ... WHERE state='running' AND lease_expires_at<:now AND attempts>=max_attempts`; :123 `no lease_expires_at>=now predicate ... Saves work after Mac sleep`; phase-04-morning-report.md:29 `Running: #id | host | lease expires in`
- **Suggested fix:** The reaper should also move `running AND lease_expires_at < now - max_stale` (e.g. 1 h) to `queued`, bumping fence so the zombie dies, with reason `lease expired on X, requeued`. Cap the heartbeat revival with `lease_expires_at >= now - revive_window` (e.g. 30 min) so short sleeps are saved and weekend zombies are not. Add an "expired leases" row to the report's Needs-attention section.

## Finding 10: Check-then-act publish window assumes nothing can stall for 5 min; a Mac sleep mid-push breaks it
- **Severity:** Medium
- **Location:** phase-03 "Who pushes / opens PR" rationale; publish steps 3-6
- **Flaw:** The argument "window between check (3) and complete (6) is far shorter than any reclaim" assumes wall-clock continuity. Steps 4-5 are network calls with no timeout, run on a laptop that sleeps (the plan relies on sleep elsewhere). On darwin the Go monotonic clock does not advance during sleep, so `task_timeout` and the heartbeat ticker also stretch across sleep. The residual race is "handled" only by `gh pr close`, which has its own failure gap (Finding 2), and the plan admits the push itself is never fenced.
- **Failure scenario:** The Mac completes the step-3 heartbeat, starts a 40 MB push, and the lid closes. 20 min later Ubuntu reclaims at f2 and finishes first, so the f2 PR merges. The Mac wakes, the push completes, the PR for f1 opens, complete returns 409, and `gh pr close` fails on DNS because wifi is not up yet. The f1 PR stays open next to a merged f2 PR, which is a duplicate PR in the soak. Also, `task_timeout=3h` measured on the monotonic clock never fires for a Mac that slept 8 h mid-run.
- **Evidence:** phase-03-host-daemon-and-claude-runner.md:98 `heartbeat just extended lease by TTL (5 min) so window between check (3) and complete (6) is far shorter than any reclaim; residual race handled by closing PR on 409`; :127 `Sleep pauses everything → lease expires → reclaim (designed for)`; :28 `task_timeout = "3h"`
- **Suggested fix:** Heartbeat again between push and `gh pr create`, and bound each git/gh call with a context timeout below TTL/2. Detect a wall-clock jump against the monotonic clock (`time.Now().Round(0)` delta) on wake and force a fence heartbeat before any further step. Measure `task_timeout` against the wall clock. Put PR close/supersede in the journal (Finding 2) so it is retried until confirmed.

## Coverage note (non-findings, verified)
- Claim race: a single `UPDATE ... WHERE id=(SELECT ... LIMIT 1) RETURNING` under SQLite's single-writer lock is atomic. The 16-claimer race test is adequate. No finding.
- Heartbeat without an expiry predicate is sound against reclaim because claim bumps fence and the reaper changes state. The risk is the unbounded revival covered in Finding 9, not fence safety.
